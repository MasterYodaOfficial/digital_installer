# Управление пользователями

## Назначение

Создание, изменение и архивирование сотрудников через рабочий кабинет с проверкой прав на сервере. Наличие изменений в исходниках не означает их установку на рабочий сервер.

## API

Рабочий экран `/users` доступен из пункта «Сотрудники». Поддерживает поиск, создание и редактирование, выбор должности, установку/замену пароля, архивирование и восстановление. Переключатель «Список» открывает действующих сотрудников или архив уволенных.

Список представлен таблицей: номер строки, фамилия, имя, логин, должность, телефон, почта, доступ ко входу и действия. Заголовок закреплён при вертикальной прокрутке, на телефоне таблица прокручивается по горизонтали. Изменения выполняются в форме, не прямым редактированием ячеек. У руководителей первой вкладкой является дашборд.

`GET /api/auth/me/` возвращает `manageable_roles` — список `{value, label}`. Карточки пользователей возвращают `can_edit`. Интерфейс использует эти признаки, но сервер повторно проверяет права каждого изменения. Ошибка сети оставляет форму открытой и не выдаётся за успешное сохранение.

- `GET /api/admin/users/` — список; фильтры `role`, `status`, `search`, `archived=true/false`. Без `archived` возвращаются все статусы для совместимости.
- `POST /api/admin/users/` — создание.
- `GET /api/admin/users/{id}/` — карточка.
- `PUT/PATCH /api/admin/users/{id}/` — изменение.
- `DELETE /api/admin/users/{id}/` — физическое удаление отключено: 405 после проверки прав (403 для защищённой записи).

Аутентификация JWT. Проверки выполняются и для прямых запросов, независимо от интерфейса.

## Права

| Исполнитель | Разрешённые роли создаваемых и изменяемых сотрудников |
|---|---|
| РП | Мастер, монтажник |
| Директор | РП, мастер, монтажник |
| Суперпользователь с ролью administrator | Все существующие бизнес-роли |
| Остальные | Нет доступа к API управления пользователями |

Директору и РП запрещено менять или архивировать собственную запись, запись с `is_staff`/`is_superuser` и запись с ролью вне разрешённого набора. Чтение списка и карточек доступно руководителям; ограничение видимости отдельных полей рассматривается отдельно.

`is_superuser=True` у директора не даёт права назначать администраторов. Технический доступ требует одновременно роль `administrator` и `is_superuser=True`.

При создании без `role` используется `worker`. Технические флаги `is_staff` и `is_superuser` не доступны для записи через сериализатор. Пароль хешируется и не возвращается; без пароля создаётся запись с непригодным для входа паролем.

## Архив и восстановление

Кнопка «В архив» запрашивает подтверждение и отправляет `PATCH` с `status=dismissed`. Сервер отключает `is_active`; запись сотрудника, пароль, связи со сменами и выполненными работами сохраняются. В архиве доступно «Восстановить»: `status=active` снова разрешает вход с прежним паролем. Редактирование имени или других полей архивной записи само по себе вход не включает.

Сотрудника или мастера открытой смены архивировать нельзя: сервер возвращает 400 с пояснением. Пока используется прежняя модель смен, нужно закрыть смену; индивидуальное завершение участия будет добавлено вместе с интервалами сотрудников.

`EmployeeJWTAuthentication` проверяет статус при каждом запросе: ранее выданный access-токен не предоставляет доступ, пока сотрудник уволен или заблокирован. `EmployeeTokenSerializer` запрещает новый вход при этих статусах, даже если в старой записи остался `is_active=True`. Это проверка текущего состояния, а не безвозвратный отзыв всех токенов: после восстановления ещё действующий токен может снова работать.

Список для выбора состава бригады скрывает недоступных сотрудников; сериализатор начала смены также отклоняет их идентификаторы. Исторический состав не очищается. Защита от одновременного начала смены и архивирования требует общей транзакционной модели смен и остаётся в плане её переработки.

## Ошибки и ограничения

- Недопустимая назначаемая роль: 400 с ошибкой поля `role`.
- Запрещённое действие авторизованного пользователя: 403.
- Отсутствие JWT обрабатывается стандартной аутентификацией DRF.
- Изменение не ограничивает Django-admin и не меняет существующие записи БД.
- Архив не заменяет аудит кадровых событий: дата увольнения, причина и автор изменения пока отдельно не записываются.

## Реализация и проверка

`backend/apps/users/permissions.py` задаёт разрешённые роли и защищённые объекты; `serializers.py` проверяет роль и переход в архив; `authentication.py` проверяет статус при входе и использовании JWT; `views.py` подключает разрешения и фильтры; `frontend/src/pages/UsersPage.jsx` реализует таблицу и диалоги. `tests.py` проверяет права, сохранение истории, архив/восстановление, вход и защиту состава новой смены.

Из `backend`: `python manage.py test apps.users --settings=config.test_settings`. База SQLite создаётся в памяти. Миграция схемы для изменения не нужна.
